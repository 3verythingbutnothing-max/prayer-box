# Cognito registration adapter: staging setup and proof

This is an implementation and setup contract, not evidence that an AWS account, user pool, IAM principal, real user, email or SMS has been created. Registration stays closed until the application capability gates, isolated provider proof and release approvals are complete. Payments remain deferred.

## Provider protocol

Cognito is the sole password authority. D1 holds application profiles, immutable provider mappings, hashed application-session/recovery material and operation state; it must not become a second password verifier.

Create a user through IAM-authorized `AdminCreateUser`, suppress its invitation, supply a random temporary password and omit contact attributes. Set the chosen permanent password with `AdminSetUserPassword`. A pool with no required contact attributes can create an account without an email address or phone number. [AdminCreateUser](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_AdminCreateUser.html), [AdminSetUserPassword](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_AdminSetUserPassword.html).

Each private, server-generated registration-intent UUID maps to `pb-<UUID>` in Cognito. This provider username is separate from the editable public handle. Never derive it from a browser idempotency value. Resume a provider duplicate only when `AdminGetUser` identifies that same temporary native account. A confirmed duplicate requires authentication with the supplied password; never replace its credentials merely because registration was retried. Unknown mutation outcomes remain reconciliation work, not permission to delete an identity.

Sign-in uses IAM-authorized `AdminInitiateAuth` with `ADMIN_USER_PASSWORD_AUTH`, followed by token-authorized `GetUser` to obtain the authoritative username and immutable `sub`. Match them to D1 before issuing an opaque application cookie. Provider tokens are discarded rather than returned to JavaScript. Every additional provider challenge is rejected by this increment; a challenge is not a signed-in user. [AdminInitiateAuth](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_AdminInitiateAuth.html), [GetUser](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_GetUser.html).

## Required pool and client configuration

- Select the **Lite** feature tier and ordinary native username/password accounts. Leave `UsernameAttributes` and alias attributes unset. Do not require email, phone, display name or unrelated personal data. Use no pre-signup Lambda for this protocol.
- Set `AllowAdminCreateUserOnly: true`. Public `SignUp` must fail: otherwise someone could bypass the application's invitations, bot checks and age gates through the Cognito API. Disable unsolicited Cognito verification/welcome messaging; the adapter explicitly suppresses admin-created invitations. [User-creation policy](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-admin-create-user-policy.html).
- Create a dedicated app client with **only** `ALLOW_ADMIN_USER_PASSWORD_AUTH` in `ExplicitAuthFlows`, `GenerateSecret: false`, `PreventUserExistenceErrors: ENABLED`, and no OAuth/managed-login domain. Do not leave default SRP, custom, refresh, passwordless or other public clients enabled for this application. IAM authorizes the admin flow; the client ID is not a secret. Choice-based `USER_AUTH` requires a higher tier and is unused here. [Client configuration](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_CreateUserPoolClient.html).
- Set password minimum length to 15, with the four character-composition requirements disabled. The adapter accepts internal ordinary spaces, rejects leading/trailing whitespace and control whitespace, and never trims or truncates. It conservatively caps at 256 UTF-16 units. The API's unanchored `\S+` schema must not be mistaken for a full-match ban on internal spaces; AWS's guide explicitly permits them. Prove these boundary cases against staging. [Password guide](https://docs.aws.amazon.com/cognito/latest/developerguide/managing-users-passwords.html), [PasswordPolicyType](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_PasswordPolicyType.html).
- Set `AccountRecoverySetting.RecoveryMechanisms` to `[{"Name":"admin_only","Priority":1}]` for this app-managed recovery protocol. Do not expose a competing public Cognito reset path when optional contacts are added later. [Recovery settings](https://docs.aws.amazon.com/cognito/latest/developerguide/managing-users-passwords.html).
- Ordinary registration creates basic sessions only. Admin/reviewer access remains denied until its separate TOTP enrollment and challenge flow is implemented and tested; do not mark a session MFA based on an app checkbox. [TOTP MFA](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-mfa-totp.html).

Configure nonsecret `COGNITO_REGION`, `COGNITO_USER_POOL_ID` and `COGNITO_CLIENT_ID` for the isolated application origin. Store `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and optional `AWS_SESSION_TOKEN` as managed Worker secrets; never commit them or expose them through Vite variables. Use temporary scoped credentials when available and rotate before expiry. Only validated commercial-partition regional endpoints are accepted. China, GovCloud and sovereign partitions need a separately reviewed adapter.

Grant the service principal only these Cognito actions against the **single staging user-pool ARN**: `AdminCreateUser`, `AdminGetUser`, `AdminSetUserPassword`, `AdminInitiateAuth`, `AdminUserGlobalSignOut`. Explicit orphan reconciliation additionally needs `AdminDeleteUser`; omit that permission when cleanup is disabled. No `GetUser` IAM permission is required because its access token authorizes it. Keep provisioning and IAM-management permissions outside this application principal. Requests use bounded SigV4 signing with no caller-controlled endpoint. [Signing requests](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv-create-signed-request.html).

## Contact-free recovery and failure boundaries

Cognito's default forgot-password flow needs a verified recovery contact, so it does not implement a contact-free recovery kit. The application must validate its high-entropy, hashed, single-use kit token and bind it to the exact account. Use `AdminSetUserPassword` against the verified immutable `sub`, then `AdminUserGlobalSignOut` against that same subject. Revoke local sessions and advance their epoch as well; Cognito token revocation does not revoke independently issued application cookies. [Recovery behavior](https://docs.aws.amazon.com/cognito/latest/developerguide/managing-users-passwords.html), [Global sign-out](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_AdminUserGlobalSignOut.html).

D1 and Cognito cannot commit one transaction. Serialize each private registration/recovery intent with a bounded lease and fence every finalization. Any ambiguous provider write must move to a non-retriable reconciliation state; a fresh client retry must not race an earlier password mutation that could still complete at AWS. Reserve a recovery token before provider mutation, prevent new application sessions while reset is unresolved, and never restore the old token after an ambiguous reset. Preserve an uncertain intent and keep the account locked for explicit staff reconciliation. Only a proven non-mutating provider rejection may allow a password edit and retry. A tested staff procedure is required before enabling the pilot. Successful recovery invalidates the old kit and requires a fresh sign-in to generate a replacement; never store plaintext codes to reproduce a lost response later. Confirmed accounts and optional contacts need separate lifecycle controls. No local password fallback or made-up email address is allowed.

The caller must enforce exact origin, bootstrap/session CSRF, server-validated Turnstile action/hostname, rate limits, invitation validity, eligibility and capability flags before invoking this adapter. Adapter configuration alone must not open registration.

## Evidence required before enabling staging registration

Tests use synthetic fetch responses only: fixed-host signing, bounded/aborted responses, identity mismatch, challenges, retry and subject-bound mutations. They do **not** prove real Cognito configuration or provider availability.

With authorized isolated test accounts, prove username-only creation, zero unsolicited messages, wrong-password and duplicate behavior, internal-space/Unicode password boundaries, request interruption at every provider/D1 boundary, contact-free recovery, global plus local revocation, revoked invite/replayed kit rejection and provider outage handling. Confirm direct public `SignUp` and unapproved public auth flows fail. Then exercise the connected UI, Cookie/CSRF protections and cross-device persistence. Do not invite the real pilot until these and the wider launch gates pass.
